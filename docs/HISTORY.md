# Development history / 开发历程

> 一份给人看的记录：这个项目怎么从「两台电脑互相看一眼」长成「跨公网的 AI 网络」的。
> A human-readable story of how dsh-mesh grew from "let two machines see each other" into a cross-internet AI mesh.

---

## 阶段 0：起点 —— 一台机器不够用 / Before the network

故事开始于一个很普通的需求：**同一个 AI 助手，为什么只能服务一台电脑？**

在 DeepSeek Harness（DSH）里，每台机器都有自己的会话、文件、终端和技能。人在公司、家、手机上切换，AI 却各自为政。最早的"跨机协作"很原始：人把任务复制到另一台机器，或者干脆远程桌面。

我们想要的是：**AI 能直接看到别的机器、把任务交给别的机器、甚至操作别的机器的桌面**。

---

## 阶段 1：局域网直连 / LAN phase

第一版只解决"同一个屋檐下"的问题。

```
   +-------------+        LAN          +-------------+
   |  DSH 节点 A  | <-----------------> |  DSH 节点 B  |
   |  mesh server |   TLS + 一次性配对码  |  mesh server |
   +-------------+                     +-------------+
```

做法很直接：

- 每个节点跑一个 mesh server（MCP over HTTPS），互相配对；
- 配对用**一次性配对码**，避免谁都能连；
- TLS 证书 + **指纹 pinning**，防止中间人；
- 先跑通两个核心能力：**看状态**（节点/实例/延迟）和**委托任务**（把一件事交给对端 AI 做，结果落盘读回）。

**局域网阶段教会我们的事：**

- 配对、信任、身份必须先解决，否则后面所有功能都是沙上建塔；
- 委托不是"发条消息"——要有任务信封、状态机、超时、结果文件，否则任务丢了都不知道；
- 但局域网也把需求边界暴露得很清楚：**出了这个网，什么都不是**。DHCP 换 IP、防火墙、跨地域，全都过不去。

---

## 阶段 2：第三方内网穿透 / NAT traversal with a hosted frp service

为了让"公司 ↔ 家"的机器互通，我们接入了第三方 frp 服务。

```
   +--------+   公网隧道   +-------------------+   公网隧道   +--------+
   | 节点 A | <----------> | 第三方 frp 服务    | <----------> | 节点 B |
   +--------+              +-------------------+              +--------+
```

这一阶段做了很多"把网络当真"的工程：

- 每个节点一条隧道，peer 记录保存公网地址 + 证书指纹；
- 指纹 pinning 在公网环境下真正发挥作用（域名/端口变了也不影响信任）；
- 设备从 2 台扩到多台，引入 **per-peer token + 最小 ACL**（默认拒绝，只放行需要的工具）；
- 开始有**审计日志**：谁在什么时候调用了什么工具。

**这一阶段教会我们的事：**

- 免费/公共隧道会抖：线路切换、限速、端口回收，都会让"看起来通"变成"时通时不通"；
- 排障成本极高——问题到底在隧道、在对端进程、还是在 DSH 引擎？于是我们补上了 `mesh-health` 一条命令体检、告警文件、看护任务；
- 当设备变多，**对称性**变得重要：不能只有"公司能委托家"，要每一台都能委托每一台。

### 一次重要的架构升级：从"点对点"到"对等 mesh"

我们把每个节点都做成同时具备两种角色：

- **host**：能被别人委托、被别人读状态、被别人控制；
- **controller**：能委托别人、能读别人、能控制别人。

这个对称模型是后面所有功能的基础——也是它区别于"远程桌面/SSH 工具"的地方。

## 阶段 3：自建公网中继 / Self-hosted relay

公共隧道的不稳定，最终让我们决定：**中继自己掌控**。

```
                     +------------------------------+
                     |     自建 frps（公网 VPS）      |
                     |  一条隧道 / 节点，TLS 转发      |
                     +--------------+---------------+
         TLS + 指纹 pin + token      |
   +---------------+--------+-------+-------+---------------+
   |               |                |               |
+--+---+       +---+--+          +--+---+       +----+----+
|  PC  |<----->|  PC  |  ...     |  PC  |<----->| 手机   |
| DSH  |       | DSH  |          | DSH  |       | dsh-go |
+------+       +------+          +------+       +--------+
```

迁移到自建中继后，我们补齐了"一个真正的网络"该有的东西：

- **一条隧道一个端口**，节点注册/健康检查/延迟全部可观测；
- 中继只做转发，**不持有凭据**；身份仍在 peer token + TLS 指纹；
- 保留**局域网直连作为快路径**，公网隧道作为兜底（同一设备可以有多个入口）；
- 手机（dsh-go）作为独立节点入网，成为控制器，可以直接操作电脑桌面；
- 自更新 / 自启 / 监督进程：节点重启后网络能自己恢复。

**这一阶段教会我们的事：**

- 中继是单点：要做好"中继挂了怎么办"的心理准备（多中继、P2P 打洞是后续方向）；
- 能直控桌面之后，**安全默认值比功能更重要**：远程控制默认关闭、每个动作白名单、需要确认、可审计、可撤销；
- 运维界面必须说人话：设备归并、节点拓扑、健康状态，一眼能看懂比功能多更重要。

---

## 阶段 4：开源 / Open source

把内部跑通的系统整理成可复用的形式：

- 四个 npm 包，对应四层能力：mesh server、DSH 宿主桥、设置页面板、引擎重启自愈；
- 公开前做**敏感信息扫描**：个人路径、内网地址、邮箱、token、设备名一律剔除；
- 面向"别人的机器"重新设计默认值：没有任何预置凭据、没有写死的服务器地址。

| 阶段 | 新增能力 |
|---|---|
| LAN | 配对码、TLS+指纹、节点状态、委托任务、结果落盘 |
| 内网穿透 | 公网 peer、每 peer token/ACL、审计、健康体检、告警 |
| 自建中继 | 对称 mesh、多隧道、LAN+公网双路径、手机节点、桌面直控、session-0 helper、自更新/自启 |
| 开源 | 通用化配置、默认安全、npm 包、公开文档 |

## 踩过的坑（也是设计的一部分）/ Lessons learned

1. **"能连上" ≠ "能用"**：先有健康检查、看护和告警，再谈功能。
2. **身份/信任是地基**：配对码、指纹 pin、per-peer token，任何一层省掉都会在公网环境付出代价。
3. **最小权限不是口号**：一次权限收窄脚本写反，反而扩大了 token 权限——后来所有 ACL 变更都必须备份 + 校验。
4. **桌面 ≠ 服务会话**：以服务方式运行的进程看不到用户桌面；这正是内置"用户会话 helper"的原因。
5. **多入口会被当成多设备**：同一台机器的 LAN/WAN/控制入口需要在展示层归并，否则拓扑会"长出"假设备。
6. **公开仓库的第一原则是"没有秘密"**：提交历史、配置、文档、注释都要过一遍敏感信息扫描。
